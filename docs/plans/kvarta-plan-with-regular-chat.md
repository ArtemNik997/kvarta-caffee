## 1. Что на самом деле оценивают

Бриф прямо говорит: смотрят **не только на итог, но и на то, как вы управляете ИИ**. Поэтому критерии, по порядку важности:

| # | Что смотрят | Что это значит для вас |
|---|---|---|
| 1 | Вид: «работа студии для конкретного клиента» | Нельзя принять первый вариант от ИИ. Нужна идея, привязанная к «Кварте» (свежесть, четверг/пятница, партии по 5 кг). |
| 2 | Форма и бэкенд | Валидация белорусского номера, защита от дублей за 10 минут (включая двойной клик), UTM-атрибуция, понятная ошибка отправки. |
| 3 | Процесс | Осмысленные коммиты, честный ручной лог работы с ИИ (запросы, решения, найденные ошибки), README. Команда `/export` не требуется. |
| 4 | Работающая ссылка | Сайт и форма должны работать **на хостинге**, а не только локально. |
| 5 | Lighthouse (mobile) | Замер приложен, результаты разумные. |
| 6 | Честность | «Неполная работа с честным README лучше, чем идеальная без объяснений». |

**Главная мысль:** работа без идеи и без следов вашего мышления проиграет работе поскромнее, но с явными решениями.

## 2. Принятые решения (кратко)

| Вопрос | Решение | Почему |
|---|---|---|
| Стек | Next.js (App Router) + TypeScript + Tailwind | Основной стек у заказчика — плюс; одна кодовая база для сайта и API. |
| Хостинг | Vercel (Hobby) | Бесплатно, нативно для Next.js, API-роуты работают сразу. |
| Хранилище заявок | **Upstash Redis** (через Vercel Marketplace) | Файл и локальный SQLite **не работают** на Vercel (файловая система serverless только для чтения/эфемерна). Redis даёт атомарную операцию `SET NX EX` — идеальную для «не создавать дубль 10 минут». |
| Запасной вариант хранилища | Turso (libSQL/SQLite) | Если Redis не подойдёт: даёт настоящую SQL-таблицу, дедуп делается атомарным `INSERT … WHERE NOT EXISTS`. |
| Валидация | Zod + общий модуль `lib/phone.ts` | Одни и те же правила на клиенте и сервере; **источник истины — сервер**. |
| Уведомления | Telegram-бот (бонус) | Дешёво, быстро, и это же вторая копия заявки. |
| Анимации | Только CSS + `IntersectionObserver` | Не тормозят Lighthouse, уважают `prefers-reduced-motion`. |
| Превью ссылки | Статичный `og.png` 1200×630 + Next Metadata API | Проще и надёжнее, чем генерировать шрифты с кириллицей в `ImageResponse`. |

> Конкретные условия бесплатных тарифов (лимиты Upstash/Vercel/Turso) меняются — перед выбором коротко проверьте их на сайтах сервисов.

## Шаг 0. Разбор брифа, ловушки, допущения

**Цель шага:** понять, что именно нужно, и заранее записать решения по тому, чего в брифе нет. Всё, что решили сами, потом идёт в README как «допущения».

### 0.1. Вопросы заказчику (разрешены брифом)

Отправьте один короткий список — ответ может не прийти, тогда фиксируйте допущение:

1. Контакты мастерской (телефон, Telegram, Instagram)? Или можно поставить заглушки?
2. Доставка по Минску **меньше** 50 BYN — сколько стоит?
3. Есть ли крайний срок заказа на пятничную доставку (например, «до среды 18:00»)?
4. Что входит в подписку: клиент выбирает сорта, или мастерская?
5. Принимать ли городские номера (+375 17 …) или только мобильные?

### 0.2. Ловушки в брифе (проверьте цифры — это и есть «думать головой»)

- **Подписка не всегда выгоднее.** Подписка: 2 пачки за 54 BYN. Но 2×Бразилия = 52 BYN (дешевле), Бразилия + Колумбия = 55, Колумбия + Эфиопия = 61, 2×Эфиопия = 64. Значит, **нельзя писать «выгодно»/«экономия» как общее утверждение**. Честная подача: «27 BYN за пачку» и «не нужно вспоминать про заказ — свежий кофе приезжает сам».
- **Бесплатная доставка — слабый аргумент подписки.** Доставка бесплатна от 50 BYN, а любые две пачки уже ≥ 52 BYN. Упоминать можно, но не делать главным преимуществом.
- **«1–3 день после обжарки»** согласуется с графиком: обжарка в четверг → доставка в пятницу (день 1) → выходные (день 2–3). Это лучшая визуальная идея сайта (см. Шаг 2).
- **Не придумывайте факты.** Степень обжарки указана только у Эфиопии («светлая»), «под эспрессо» — только у Бразилии. Для остальных не добавляйте характеристик, которых нет в брифе. Вес и вкус дрип-пакетов тоже не указаны.
- **Фото основателей.** Аня и Дмитрий вымышленные. Не подписывайте стоковые лица их именами. Используйте руки, обжарочную машину, пачки, интерьер — или иллюстрацию.

### 0.3. Список допущений (создайте файл `NOTES.md` и ведите его с первой минуты)

Минимум, который почти наверняка пригодится:

```md
## Допущения
- Контакты мастерской — заглушки (+375 29 000-00-00, @kvarta_roastery). В брифе их нет.
- Доставка до 50 BYN: «стоимость уточнит менеджер».
- Срока приёма заказов на пятницу нет: «Принимаем заявки всю неделю, развозим по пятницам».
- Состав подписки: менеджер уточняет сорта при звонке (поле «комментарий»).
- Телефон: принимаются мобильные коды 25, 29, 33, 44.
- Повторная заявка с того же номера за 10 минут = «успех» для пользователя, но новая запись не создаётся.
- Оплата: обсуждается с менеджером (онлайн-оплаты нет по брифу).

## Где ИИ ошибся (заполнять по ходу работы)
- …

## Что не успел / сделал бы иначе
- …
```

**Ведите блок «Где ИИ ошибся» сразу, в момент ошибки.** К вечеру понедельника вы это не вспомните, а для README это один из обязательных пунктов.

**Готово, когда:** есть `NOTES.md` с допущениями, вопросы заказчику отправлены.

### 1.5. Работа через обычный чат: ручной цикл

В обычном чате ИИ **не видит файлы на вашем компьютере, не может сам сохранить код в проект и не запускает ваши команды**. Поэтому работайте короткими итерациями. Не просите сразу «создать весь сайт»: при большом ответе трудно понять, какой код куда вставлять и где искать ошибку.

**Один цикл работы выглядит так:**

1. В чате опишите одну небольшую задачу и укажите путь к файлу, например `components/sections/Hero.tsx`.
2. Попросите ИИ сначала перечислить, какие файлы он собирается создать или изменить. На первом проходе — обычно один файл; допустимо несколько, только если они действительно неразделимы.
3. Попросите выдать **полное содержимое файла**, а не фрагменты с «вставьте сюда». Если файл уже существует, сначала отправьте его актуальное содержимое в чат.
4. Создайте файл/замените содержимое в редакторе (например, VS Code), сохраните его и запустите указанные команды: `npm run dev`, `npm run lint`, тесты или `npm run build`.
5. Если есть ошибка — отправьте в тот же чат полный текст ошибки, команду, которую запускали, и путь к файлу. Не переписывайте код наугад.
6. Проверьте страницу в браузере, при необходимости приложите скриншот и попросите изменить только то, что не работает или выглядит не так.
7. Когда этап работает, сделайте Git-коммит. После этого переходите к следующей задаче.

Создайте `docs/ai-context.md` — короткую памятку, которую можно вставлять в новый чат, если потеряется контекст:

```md
# Контекст проекта «Кварта»
- Проект: лендинг небольшой обжарки кофе в Минске.
- Стек: Next.js App Router, TypeScript, Tailwind CSS.
- Концепция: сайт как этикетка пачки кофе; дата обжарки и недельный цикл — ключевые элементы.
- Стиль: тёплая бумажная палитра, выразительная типографика, асимметрия; без градиентов, glassmorphism и шаблонных карточек.
- Тексты и факты сверять с брифом и NOTES.md. Ничего не выдумывать.
- Не добавлять зависимости без объяснения и моего согласия.
- Менять небольшие части за раз; перед правкой существующего файла попросить его текущий код.
- После кода указывать путь файла и команды для проверки.
- Секреты из .env.local не вставлять в чат и не коммитить.
```

Для фиксации процесса создайте `docs/ai-session.md`. Заполняйте его вручную в процессе, а не в последний момент: дата, цель запроса, краткое содержание ответа, что вы проверили, что исправили и какое решение приняли сами. Сохраните 3–5 скриншотов ключевых моментов чата (дизайн-направление, исправленная ошибка, проверка формы). **Не утверждайте, что это экспорт всей сессии**: это ваш журнал работы с ИИ. Если в задании явно требуется полный экспорт чата, приложите доступный экспорт/копию переписки обычного чата, если интерфейс это позволяет.

## Шаг 2. Дизайн-направление (до написания кода)

Это самый важный шаг по критерию «не выглядит сгенерированным». **Не пишите вёрстку, пока не выбрана идея.**

### 2.1. Почему лендинги «видно, что сгенерированы»

Заведомо избегайте:

- фиолетово-синих градиентов и «сияющих» блобов на фоне;
- тёмного фона с фото кофейных зёрен «как в рекламе премиум-кофе» (бриф прямо просит без глянца и пафоса);
- центрированного hero: огромный заголовок + подзаголовок + две кнопки;
- одинаковых карточек в 3 колонки с иконкой в круге и всеми углами `rounded-2xl`;
- стеклянных (glassmorphism) карточек, теней «везде»;
- эмодзи вместо иконок (☕🚚);
- шрифтов по умолчанию (Inter/Geist + одинаковый вес везде);
- текстов вида «Погрузитесь в мир кофе», «Уникальный», «Премиальный», «Каждая чашка — история»;
- симметрии и одинаковых отступов между всеми секциями.

### 2.2. Идея: «этикетка и календарь обжарки»

Свежесть — единственное, что продают. Значит, сайт должен **показывать время**, а не говорить о нём. Центральная метафора: **сайт — это пачка кофе с этикеткой**, где важнее всего дата обжарки.

Конкретные приёмы:

1. **Штамп с датой обжарки в hero.** Вычисляется по текущей дате (Europe/Minsk): «Обжарено: чт, 15 октября · Следующая партия: 22 октября». Это сразу объясняет продукт и выглядит как специфичная фишка именно этого клиента.
2. **Недельная лента «Чт → Пт → Сб → Вс»** в блоке про свежесть: четверг — обжарка (партия 5 кг), пятница — развозим по Минску (день 1), выходные — день 2–3. Без стоковых иконок: рисуется типографикой и линией.
3. **Карточки товаров — как этикетки на пачках:** крупное название, «в чашке: …», рамка/перфорация, номер «партии», у каждого сорта свой акцентный цвет из палитры.
4. **Язык «бумажной упаковки»:** тёплая бумажная подложка, тонкие линии, штампы, моноширинный шрифт для служебных пометок (дата, вес, номер партии).
5. **Ассиметричная сетка**, крупные числа (32 / 29 / 26 BYN), выравнивание по левому краю, а не всё по центру.

Дополнительная идея-на-выбор (не обязательно): имя «Кварта» ≈ «четверть» — четверть круга как знак и четыре «опорных» этапа недели.

### 2.3. Токены дизайна

Определите их **до** вёрстки и держите только в `globals.css` (Tailwind v4):

### 2.4. Типографика

- Нужны **кириллические** шрифты. Стартовый набор: заголовки — `Literata` (тёплая антиква), текст — `Onest`, служебные пометки — `IBM Plex Mono`. Можно заменить (например, `Geologica`, `Golos Text`), но проверьте поддержку кириллицы.
- Подключение через `next/font` (self-host, без внешнего запроса, меньше CLS):

## Шаг 4. Вёрстка секций (mobile-first)

Аудитория: 25–45 лет, **большинство — с телефона по рекламе** в Instagram/Яндексе. Поэтому верстаем под ширину **360–390 px** и затем расширяем на планшет/десктоп. Открывать страницу будут в встроенном браузере Instagram — проверяйте и там.

### 4.1. Общие правила

- Контейнер `max-w-6xl`, боковые отступы 16–20 px на мобильном.
- Минимальная зона нажатия — 44–48 px.
- Контраст текста ≥ 4.5:1 (особенно `muted`-цвет на `paper` — частая ошибка у тёплых палитр).
- У каждого `<img>` указаны размеры или `aspect-ratio` (иначе CLS).
- Семантика: `header`, `main`, `section` с `aria-labelledby`, один `h1`.
- Якоря с `scroll-margin-top`, чтобы липкая шапка не перекрывала заголовок.
- Все кнопки CTA ведут к форме (`#lead`).

### 4.2. Секции по одной

**Шапка**
- Что: текстовый логотип «Кварта» (можно с деталью: четверть круга/штамп), 3–4 якоря, кнопка.
- Как: на мобильном — логотип + одна кнопка «Заявка», без бургер-меню (меньше JS).

**Hero + штамп обжарки**
- Что: заголовок, подзаголовок, 2 кнопки, фото (руки/пачка/обжарщик), штамп с датами.
- Как: асимметрия (текст слева, штамп наклонён на 2–4°, частично накладывается на фото). Штамп — компонент `RoastStamp`.
- Даты считаются по Europe/Minsk; на клиенте после монтирования (чтобы не было рассинхрона SSR/клиента), место под штамп зарезервировано, чтобы не было CLS:

```ts
// lib/roast-calendar.ts
export function roastCalendar(now = new Date()) {
  // «Минское» время без сторонних библиотек
  const minsk = new Date(now.toLocaleString("en-US", { timeZone: "Europe/Minsk" }));
  const dow = minsk.getDay();                 // 0=вс … 4=чт … 6=сб
  const sinceThu = (dow - 4 + 7) % 7;         // сколько дней прошло с четверга
  const lastRoast = new Date(minsk); lastRoast.setDate(minsk.getDate() - sinceThu);
  const nextRoast = new Date(lastRoast); nextRoast.setDate(lastRoast.getDate() + 7);
  const fmt = (d: Date) => d.toLocaleDateString("ru-RU", { day: "numeric", month: "long" });
  const wd  = (d: Date) => d.toLocaleDateString("ru-RU", { weekday: "short" });
  return { last: `${wd(lastRoast)}, ${fmt(lastRoast)}`, next: `${wd(nextRoast)}, ${fmt(nextRoast)}` };
}
```

(Допущение: в сам четверг «последняя обжарка» — сегодняшняя. Запишите в `NOTES.md`.)

**Свежесть (лента недели)**

## Шаг 5. Форма заявки (фронтенд)

### 5.1. Поля

### 5.2. Валидация белорусского номера (модуль `lib/phone.ts`)

Принимаем форматы: `+375 29 123-45-67`, `375291234567`, `8 029 123-45-67`, `29 123 45 67`. Приводим к единому виду `+375XXXXXXXXX`.

```ts
// lib/phone.ts
const MOBILE_CODES = ["25", "29", "33", "44"]; // life:), A1, MTS — допущение, см. NOTES.md

export type PhoneResult =
  | { ok: true; value: string }              // «+375291234567»
  | { ok: false; reason: "empty" | "format" | "code" };

export function normalizeByPhone(input: string): PhoneResult {
  const raw = input.trim();
  if (!raw) return { ok: false, reason: "empty" };

  let d = raw.replace(/\D/g, "");

  if (d.length === 11 && d.startsWith("80")) d = "375" + d.slice(2); // 8 029 …
  else if (d.length === 9) d = "375" + d;                            // 29 123 45 67

  if (d.length !== 12 || !d.startsWith("375")) return { ok: false, reason: "format" };
  if (!MOBILE_CODES.includes(d.slice(3, 5)))   return { ok: false, reason: "code" };

  return { ok: true, value: "+" + d };
}

export const PHONE_MESSAGES = {
  empty:  "Укажите телефон — по нему мы перезвоним.",
  format: "Похоже, номер неполный. Пример: +375 29 123-45-67",
  code:   "Нужен белорусский мобильный: код оператора 25, 29, 33 или 44.",
} as const;
```

Проверьте руками хотя бы эти случаи (и покройте тестами в `tests/phone.test.ts`):

| Ввод | Ожидание |
|---|---|
| `+375 (29) 123-45-67` | ✅ `+375291234567` |
| `8 029 123 45 67` | ✅ `+375291234567` |
| `29 123 45 67` | ✅ `+375291234567` |
| `+375 29 123-45-6` | ❌ `format` |
| `+7 912 345-67-89` (РФ) | ❌ `format` |
| `+375 99 123-45-67` | ❌ `code` |
| пусто | ❌ `empty` |

> Если ответ заказчика допускает городские номера (например, Минск `17`), добавьте код в `MOBILE_CODES` и обновите допущение.

**Форматирование при вводе:** не подключайте тяжёлую библиотеку масок. Достаточно подсказки в `placeholder` («+375 29 123-45-67») и «причёсывания» номера по `blur`. Слишком агрессивные маски ломают удаление символов на мобильном.

### 5.3. Состояния формы

```
idle → submitting → success
              ↘ error (сеть/сервер) → (повтор) → submitting
idle → (ошибка валидации поля) → idle
```

Что видит человек:

- **Ошибка поля:** текст под полем (не `alert`), поле подсвечено, фокус на первом неверном поле, `aria-invalid`, ошибки в `aria-live="polite"`.
- **Отправка:** кнопка заблокирована, текст «Отправляем…», данные не стираются.
- **Успех:** вместо формы — спокойное сообщение: «Заявка принята. Перезвоним в рабочее время (пн–пт 8:00–20:00, сб–вс 10:00–18:00)».
- **Ошибка отправки (обязательное требование брифа):** блок с понятным текстом и действием:
  > «Не получилось отправить заявку. Данные в форме сохранены. Нажмите «Повторить» или позвоните нам: +375 29 000-00-00 / напишите в Telegram @kvarta_roastery».
  Кнопка «Повторить» и запасные контакты обязательны.
- **Повторная заявка того же номера:** сервер вернёт «успех» — пользователь увидит то же сообщение об успехе (так проще и не пугает).

### 5.4. Защита от двойного нажатия (слой 1 из 3)

```tsx
const lock = useRef(false);

async function onSubmit(e: React.FormEvent) {
  e.preventDefault();
  if (lock.current) return;                    // двойной клик/тап игнорируется
  const errors = validate(values);             // та же логика, что и на сервере
  if (errors) { setErrors(errors); focusFirstError(errors); return; }

  lock.current = true;
  setStatus("submitting");
  const ctrl = new AbortController();
  const timer = setTimeout(() => ctrl.abort(), 10_000);   // не висим вечно

  try {
    const res = await fetch("/api/lead", {
      method: "POST",
      headers: { "Content-Type": "application/json" },
      body: JSON.stringify({ ...values, attribution: getAttribution(), page_url: location.href }),
      signal: ctrl.signal,
    });
    const data = await res.json().catch(() => null);

    if (res.status === 422 && data?.errors) { setErrors(data.errors); setStatus("idle"); return; }
    if (!res.ok) throw new Error("server");
    setStatus("success");
  } catch {
    setStatus("error");                         // сеть, таймаут, 5xx
  } finally {
    clearTimeout(timer);
    lock.current = false;
  }
}
```

Три слоя защиты от дублей работают вместе:
1. **UI:** `lock` + `disabled` на кнопке.
2. **Сервер:** атомарный `SET NX EX 600` по номеру (Шаг 6).
3. **Сценарий «запрос дошёл, ответ потерялся»:** пользователь нажимает «Повторить», сервер видит тот же номер и отвечает успехом, не создавая вторую запись.

## Шаг 6. Бэкенд `POST /api/lead`

### 6.1. Контракт API

| Статус | Тело | Когда |
|---|---|---|
| `201` | `{ ok: true, id }` | заявка создана |
| `200` | `{ ok: true, duplicate: true }` | тот же номер за последние 10 минут — **новая заявка не создана** |
| `400` | `{ ok: false, error: "bad_request" }` | невалидный JSON/слишком большое тело |
| `422` | `{ ok: false, errors: { phone: "…", name: "…" } }` | ошибки полей |
| `429` | `{ ok: false, error: "rate_limited" }` | слишком много запросов с одного IP |
| `500` | `{ ok: false, error: "storage" }` | не удалось сохранить |

### 6.2. Выбор хранилища (нужно объяснить в README)

**Почему не файл и не SQLite-файл:** на Vercel код работает в serverless-функциях: файловая система не предназначена для постоянной записи, данные пропадут между вызовами/деплоями. Файл/SQLite подошёл бы только для VPS или локального запуска.

**Выбор: Upstash Redis.**
- Подключается через Vercel Marketplace (ключи прописываются в переменные окружения автоматически).
- Операция `SET key value NX EX 600` атомарна: «поставь ключ, только если его нет, и удали через 10 минут» — идеально для окна дедупликации. Даже 5 одновременных запросов дадут ровно одну запись.
- Заявки складываем в список `leads` (JSON-строки). Для менеджера они дополнительно приходят в Telegram.

**Альтернатива: Turso (SQLite в облаке)**, если хочется SQL-таблицу. Атомарный дедуп одним запросом:

```sql
INSERT INTO leads (id, created_at, phone, name, interest, comment, utm_source, /* … */)
SELECT ?, ?, ?, ?, ?, ?, ?, /* … */
WHERE NOT EXISTS (
  SELECT 1 FROM leads WHERE phone = ? AND created_at > datetime('now', '-10 minutes')
);
-- rowsAffected = 0 → дубль
```

### 6.4. Обработчик

Порядок действий критичен:

1. Прочитать JSON (ошибка → 400).
2. Ловушка `website`: если заполнена — **тихо вернуть 200** (бот не должен понять, что его отсекли).
3. Валидация по Zod; номер нормализовать и проверить на сервере (422).
4. (Опционально) ограничение по IP.
5. **Занять ключ дедупликации** `SET NX EX 600`. Не получилось → `200 duplicate`.
6. Сохранить заявку. Если сохранение упало — **удалить ключ**, иначе человек не сможет повторить 10 минут.
7. Отправить в Telegram (best effort: ошибка Telegram не должна ломать приём заявки).
8. Вернуть `201`.

```ts
// app/api/lead/route.ts
import { NextResponse } from "next/server";
import { createHash, randomUUID } from "node:crypto";
import { Redis } from "@upstash/redis";
import { LeadSchema } from "@/lib/lead-schema";
import { normalizeByPhone, PHONE_MESSAGES } from "@/lib/phone";
import { notifyTelegram } from "@/lib/telegram";

export const runtime = "nodejs";
const redis = Redis.fromEnv();
const DEDUP_TTL_SEC = 600; // 10 минут

export async function POST(req: Request) {
  // 1. тело запроса
  let body: unknown;
  try {
    const text = await req.text();
    if (text.length > 10_000) throw new Error("too_big");
    body = JSON.parse(text);
  } catch {
    return NextResponse.json({ ok: false, error: "bad_request" }, { status: 400 });
  }

  // 2. honeypot
  if (typeof (body as any)?.website === "string" && (body as any).website !== "") {
    return NextResponse.json({ ok: true });
  }

  // 3. валидация
  const parsed = LeadSchema.safeParse(body);
  const errors: Record<string, string> = {};
  if (!parsed.success) {
    for (const issue of parsed.error.issues) errors[String(issue.path[0] ?? "form")] = issue.message;
  }
  const phone = normalizeByPhone(String((body as any)?.phone ?? ""));
  if (!phone.ok) errors.phone = PHONE_MESSAGES[phone.reason];
  if (Object.keys(errors).length || !parsed.success || !phone.ok) {
    return NextResponse.json({ ok: false, errors }, { status: 422 });
  }

  // 4. (опционально) лимит по IP
  const ip = (req.headers.get("x-forwarded-for") ?? "unknown").split(",")[0].trim();
  const hits = await redis.incr(`rl:${ip}`);
  if (hits === 1) await redis.expire(`rl:${ip}`, 600);
  if (hits > 10) return NextResponse.json({ ok: false, error: "rate_limited" }, { status: 429 });

  // 5. дедуп: атомарно «занять» номер на 10 минут
  const id = randomUUID();
  const dedupKey = `dedup:${createHash("sha256").update(phone.value).digest("hex")}`;
  const claimed = await redis.set(dedupKey, id, { nx: true, ex: DEDUP_TTL_SEC });
  if (!claimed) return NextResponse.json({ ok: true, duplicate: true }, { status: 200 });

  // 6. сохранение
  const lead = {
    id,
    created_at: new Date().toISOString(),
    name: parsed.data.name,
    phone: phone.value,
    interest: parsed.data.interest,
    comment: parsed.data.comment,
    attribution: parsed.data.attribution ?? {},
    page_url: parsed.data.page_url ?? "",
    user_agent: req.headers.get("user-agent")?.slice(0, 300) ?? "",
  };
  try {
    await redis.lpush("leads", JSON.stringify(lead));
  } catch {
    await redis.del(dedupKey).catch(() => {});      // дать возможность повторить
    return NextResponse.json({ ok: false, error: "storage" }, { status: 500 });
  }

  // 7. Telegram — best effort
  await notifyTelegram(lead).catch(() => {});

  return NextResponse.json({ ok: true, id }, { status: 201 });
}
```

> Чего нет в примере, но стоит добавить: проверку `Content-Type`, «санитизацию» строк (удаление управляющих символов) и логирование ошибок (`console.error`) без телефонов в логах.

### 6.5. Просмотр заявок (по желанию)

Маленький защищённый эндпоинт `GET /api/leads` с заголовком `Authorization: Bearer $ADMIN_TOKEN`, возвращающий последние 50 заявок (`LRANGE leads 0 49`). Либо просто скриншот данных из консоли Upstash в README. Нужен, чтобы проверяющий мог убедиться: заявки реально сохраняются.

## Шаг 7. Атрибуция: откуда пришёл клиент

**Требование:** менеджеру важно знать, **из какой рекламы, с какого объявления, с какой страницы** пришёл клиент.

### 7.1. Что собираем

| Что | Откуда | Зачем |
|---|---|---|
| `utm_source`, `utm_medium`, `utm_campaign`, `utm_content`, `utm_term` | URL при входе | какая реклама, кампания, объявление |
| `yclid` | Яндекс.Директ добавляет автоматически | признак Яндекса |
| `fbclid` | Instagram/Facebook добавляют к ссылкам | признак Instagram/Meta |
| `gclid` | Google Ads | на всякий случай |
| `referrer` | `document.referrer` | откуда перешёл (часто пустой в Instagram) |
| `landing_url` | URL **первой** страницы с параметрами | с какой страницы/посадочной |
| `page_url` | URL в момент отправки формы | где человек отправил |

### 7.2. Как сохранять на клиенте

Параметры нужны не в момент входа, а в момент отправки формы — значит, их надо **запомнить**. Логика: сохраняем, когда в URL есть рекламные параметры (перезаписываем — «последний рекламный клик»), либо когда ещё ничего не сохранено (органика/прямой заход).

```ts
// lib/attribution.ts
const KEYS = ["utm_source","utm_medium","utm_campaign","utm_content","utm_term","yclid","fbclid","gclid"] as const;
const STORE = "kvarta_attr_v1";

export function captureAttribution() {
  try {
    const params = new URLSearchParams(location.search);
    const found: Record<string, string> = {};
    for (const k of KEYS) { const v = params.get(k); if (v) found[k] = v.slice(0, 200); }

    const hasAdParams = Object.keys(found).length > 0;
    if (hasAdParams || !localStorage.getItem(STORE)) {
      localStorage.setItem(STORE, JSON.stringify({
        ...found,
        referrer: document.referrer || "",
        landing_url: location.href,
      }));
    }
  } catch { /* приватный режим/встроенный браузер: не ломаем страницу */ }
}

export function getAttribution() {
  try { return JSON.parse(localStorage.getItem(STORE) || "{}"); } catch { return {}; }
}
```

- Вызывать `captureAttribution()` один раз при загрузке (клиентский компонент `AttributionCapture` в `layout.tsx`, `useEffect`).
- Всё в `try/catch`: встроенные браузеры соцсетей и приватные режимы иногда запрещают `localStorage`. По желанию добавьте запасной вариант через `sessionStorage` или cookie.

### 7.3. Как это читает менеджер

На сервере добавьте **человекочитаемую «догадку об источнике»**, если `utm_source` не задан:

```ts
function guessSource(a: Record<string, string | undefined>) {
  if (a.utm_source) return `${a.utm_source}${a.utm_medium ? " / " + a.utm_medium : ""}`;
  if (a.yclid)  return "Яндекс (по yclid)";
  if (a.fbclid) return "Instagram/Meta (по fbclid)";
  if (a.gclid)  return "Google (по gclid)";
  return a.referrer ? `переход с ${a.referrer}` : "прямой заход / неизвестно";
}
```

Instagram/Meta (динамические параметры объявления):


## Шаг 8. Дублирование заявок в Telegram

Не обязательно, но это быстрый плюс.

### 8.1. Настройка бота

1. В Telegram откройте `@BotFather` → `/newbot` → получите **токен**.
2. Напишите вашему боту любое сообщение (или добавьте бота в группу и напишите в ней).
3. Получите `chat_id`: откройте `https://api.telegram.org/bot<TOKEN>/getUpdates` и найдите `chat.id`.
4. Добавьте `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID` в `.env.local` и в переменные окружения Vercel.

### 8.2. Отправка

```ts
// lib/telegram.ts
const esc = (s: string) => s.replace(/&/g, "&amp;").replace(/</g, "&lt;").replace(/>/g, "&gt;");

export async function notifyTelegram(lead: any) {
  const token = process.env.TELEGRAM_BOT_TOKEN, chat = process.env.TELEGRAM_CHAT_ID;
  if (!token || !chat) return;                       // без настройки — молча пропускаем

  const a = lead.attribution ?? {};
  const interest = { subscription: "Подписка", "one-time": "Разовый заказ", question: "Вопрос" }[lead.interest as string] ?? lead.interest;
  const text = [
    "<b>Новая заявка «Кварта»</b>",
    `Имя: ${esc(lead.name)}`,
    `Телефон: ${esc(lead.phone)}`,
    `Интересует: ${esc(String(interest))}`,
    lead.comment ? `Комментарий: ${esc(lead.comment)}` : "",
    "",
    `Источник: ${esc(guessSource(a))}`,
    a.utm_campaign ? `Кампания: ${esc(a.utm_campaign)}` : "",
    a.utm_content  ? `Объявление: ${esc(a.utm_content)}` : "",
    `Страница: ${esc(lead.page_url || a.landing_url || "—")}`,
  ].filter(Boolean).join("\n");

  await fetch(`https://api.telegram.org/bot${token}/sendMessage`, {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ chat_id: chat, text, parse_mode: "HTML" }),
    signal: AbortSignal.timeout(4000),               // не ждём Telegram дольше 4 с
  });
}
```

Важные моменты:
- **Экранирование HTML** обязательно — иначе комментарий с `<` сломает сообщение (или вставит разметку).
- Ошибка/таймаут Telegram **не должны** превращаться в ошибку для клиента (заявка уже сохранена).
- Токен бота нигде не светится в коде и репозитории.

**Готово, когда:** новая заявка приходит в Telegram с источником и страницей; дубль за 10 минут второго сообщения не создаёт.

## Шаг 10. Анимации

Бонус, **только если они уместны и не тормозят**. Идеи, привязанные к смыслу:

- Штамп «ставится» на этикетку при загрузке (короткая анимация масштаба/поворота, 300–400 мс).
- Линия недели («Чт → Пт → Сб») «прорисовывается» при прокрутке.
- Мягкое появление блоков (`opacity` + `translateY`) через `IntersectionObserver`.

Правила:

- Анимировать только `transform` и `opacity` (не `width/height/top/left`).
- **Без тяжёлых библиотек** (GSAP, Framer Motion) ради двух эффектов — CSS достаточно.
- Обязательно:

```css
@media (prefers-reduced-motion: reduce) {
  * { animation: none !important; transition: none !important; }
}
```

- Нельзя, чтобы контент был невидим, пока не загрузится JS (иначе пострадает LCP и пользователи без JS увидят пустоту). Начальное состояние «видимо», анимации — прогрессивное улучшение.
- Hero-контент не анимируем «с нуля» (влияет на LCP).

**Готово, когда:** анимации подчёркивают идею (свежесть/время), не мешают чтению и не ухудшают Lighthouse.

## Шаг 11. Деплой

1. Подключите GitHub-репозиторий к Vercel (Import Project). Определится Next.js автоматически.
2. В Vercel → Storage / Marketplace добавьте **Upstash Redis** и подключите к проекту — переменные подставятся автоматически (проверьте, что их названия совпадают с теми, что использует `Redis.fromEnv()`; иначе создайте клиент явно: `new Redis({ url, token })`).
3. Добавьте остальные переменные: `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`, `ADMIN_TOKEN`.
4. Задеплойте. Откройте **продакшен-ссылку** (не preview) и:
   - отправьте тестовую заявку → проверьте запись в Redis и сообщение в Telegram;
   - проверьте повторную отправку (дубль);
   - проверьте ошибку (временно подставьте неверный токен хранилища в preview и убедитесь, что пользователь видит ошибку; верните обратно).
5. Откройте сайт **на реальном телефоне** — и в обычном браузере, и из ссылки внутри Instagram (отправьте ссылку себе в Direct).
6. Обновите `metadataBase` на финальный домен, перепроверьте превью.

Если Vercel вам не подходит — Netlify/Cloudflare Pages, но тогда проверьте, как у них работают серверные функции и какое хранилище доступно.

**Готово, когда:** по публичной ссылке сайт открывается, форма сохраняет заявки, Telegram получает уведомление.

## Шаг 12. Lighthouse для мобильной версии

### 12.1. Как замерять

- Замер **на продакшен-ссылке**, не на `localhost` (на dev-сервере результат искажён).
- Вариант 1: Chrome DevTools → Lighthouse → режим **Mobile**, категории Performance/Accessibility/Best Practices/SEO, окно **в режиме инкогнито** (без расширений).
- Вариант 2: PageSpeed Insights (`pagespeed.web.dev`) — вкладка «Мобильные».
- Запускайте 3 раза и берите медиану; сохраните скриншот или JSON-отчёт в `docs/lighthouse-mobile.*`. Указывайте дату и версию в README.

### 12.2. Типичные причины плохих баллов и как их устранить

| Проблема | Решение |
|---|---|
| Медленный LCP | Hero-фото: правильный размер, WebP/AVIF, `next/image` с `priority`, `sizes`; никакого фонового `background-image` для главного фото |
| CLS (прыжки) | `width/height` у всех изображений, резерв места под штамп и динамические блоки, `next/font` |
| Тяжёлый JS | Минимум клиентских компонентов (`"use client"` только где нужно), нет лишних библиотек |
| Шрифты | `next/font` + `display: swap`, подключать только нужные начертания и subsets |
| Сторонние скрипты (Метрика, пиксели) | Не подключайте без необходимости; если подключаете — отложенно (`afterInteractive`/`lazyOnload`) |
| Доступность | Контраст ≥ 4.5:1, `alt` у картинок, `label` у полей, видимый фокус, размер зон нажатия |
| SEO | `title`, `meta description`, `lang`, читаемые ссылки, `viewport` |
| Карта | Вместо iframe — статичное изображение + ссылка |

Целевые ориентиры: Performance ≥ 90, Accessibility ≥ 95, Best Practices ≥ 95, SEO ≥ 95. Если что-то не достигнуто — **честно напишите в README, почему** (это ценится больше, чем скрытая цифра).

**Готово, когда:** в репозитории лежит отчёт/скриншот мобильного Lighthouse с датой, а README содержит 2–3 строки: что нашли и что исправили.

## Приложение A. Как управлять ИИ в обычном чате

Это прямо отмеченная в брифе часть оценки. Отсутствие Claude Code не означает, что нужно просить один чат написать весь проект за вас. Покажите осмысленные решения и собственную проверку результата.

### Рабочие правила

1. **Сначала решение, потом код.** Дизайн-концепция, тексты, схема формы и критерии дедупликации должны быть понятны вам до реализации.
2. **Одна задача за раз.** Сначала hero, затем лента свежести, затем каталог. Не заказывайте все секции, API, Telegram и SEO в одном сообщении.
3. **Всегда называйте путь файла.** Например: «Создай полный файл `components/sections/Freshness.tsx`». Если файл уже существует — вставляйте в чат его текущее содержимое.
4. **Просите полный файл и явные зависимости.** Уточняйте, какие импорты нужны, какие пакеты нужно установить и какие команды запустить. Не вставляйте фрагмент в случайное место, если ИИ не указал точно куда.
5. **Не давайте ИИ незаметно менять архитектуру.** «Не меняй другие файлы. Если для решения нужны изменения в другом файле, сначала перечисли их и объясни зачем».
6. **Проверяйте после каждого небольшого изменения.** Сохраните файл, запустите приложение, посмотрите страницу, запускайте lint/build/tests там, где это уместно.
7. **Для исправления ошибки передавайте факты.** Отправляйте полный текст ошибки, команду, имя файла и при необходимости код проблемного файла. Не сообщайте секреты из `.env.local`.
8. **Сохраняйте свои решения.** Запишите в `NOTES.md`, почему выбрали такой подход, что отклонили и где ИИ ошибся.
9. **Коммитьте рабочие этапы.** Если новая правка сломала страницу, можно вернуться к последнему работающему коммиту.
10. **Не выдумывайте результаты.** Lighthouse, проверка API, отсутствие дублей и получение Telegram-сообщения должны быть реально проверены, а не просто заявлены ИИ.
